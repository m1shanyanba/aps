# Предметная область варианта №26

Сервер онлайн-игры принимает действия подключённых игроков. Один запрос описывает одно действие, например перемещение, атаку или применение способности. Обработчик проверяет действие по правилам игры, применяет результат к состоянию мира и формирует ответ. СМО описывает поток запросов, ожидание и расход ресурса обработчиков. Любой обработчик может обработать запрос любого клиента.

## Игровые клиенты и поступление заявок

В модели есть конечное число клиентов K. Каждый клиент считается бесконечным источником по ИБ. Пока идёт генерация, клиент планирует следующее действие независимо от того, ждут ли предыдущие запросы в буфере, обслуживаются ли они или уже покинули систему. Заявка идентифицируется клиентом и порядковым номером действия у этого клиента. Тип действия хранится для интерпретации заявки, а дисциплины работают по позициям буфера, порядку постановки и состояниям приборов.

Для ИЗ2 интервал между соседними действиями равен τ = a + (b − a) × U, где U ∈ [0, 1), 0 < a < b. Нижняя граница моделирует минимальную паузу между действиями, верхняя ограничивает паузу в рассматриваемом отрезке активной игры. Равномерный закон даёт простую модель ограниченного разброса, когда распределение реальных интервалов неизвестно. Параметры a и b задаются для источника. Интервалы выбираются независимо для каждого нового действия.

## Обработчики и время обслуживания

Модель содержит M равноправных обработчиков. Обработчик может выполнять только один запрос одновременно. При старте запроса независимо выбирается длительность ПЗ1 по формуле t = −ln(U) / μ, где U ∈ (0, 1), μ > 0. Для однородных обработчиков используется общий μ. Средняя длительность равна 1 / μ.

Экспоненциальное распределение в этой абстракции допускает как короткие действия, так и редкие долгие проверки и обновления. Отсутствие памяти описывает принятое допущение о длительности, а числовые параметры в будущем можно проверить на данных. Модель учитывает время серверной обработки. Транспортная задержка и состояние сети в показатели не входят.

## Буфер и перегрузка

Все заявки проходят через общий буфер фиксированной вместимости N. Диспетчер постановки ищет ближайшую к началу пустую ячейку по Д1ОЗ3. Заявка может покинуть её в том же модельном времени, если диспетчер выбора находит свободный обработчик. Если обработчики заняты, запрос ждёт в буфере.

Когда новое действие поступает в заполненный буфер, по Д1ОО4 теряется последнее помещённое туда из ещё ожидающих действий. Причиной потери служит перегрузка буфера. Новый запрос занимает освободившееся место. Занятый обработчик просто недоступен для нового назначения и продолжает текущую обработку.

При освобождении обработчика диспетчер выбора снова подбирает пару. Д2П2 задаёт порядок обхода обработчиков от УП. Д2Б3 задаёт порядок обхода ячеек от УБ. В обоих случаях после конца массива обход продолжается с первой позиции. Кольцевой порядок распределяет начала поисков по позициям. Конкретная длительность использования каждого обработчика зависит также от времени его обслуживания.

## Что видит наблюдатель

В пошаговом режиме ОД2 формализованная схема показывает текущие состояния клиентов, ячеек и обработчиков, положения УБ и УП, модельное время и текущие показатели. Рядом отображается календарь предстоящих особых событий. В автоматическом режиме ОР1 наблюдатель получает таблицы по источникам и приборам после завершения прогона.
